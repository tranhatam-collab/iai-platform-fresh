# TRUST_ROLE_BOUNDARY.md

**Version:** 1.0  
**Date:** 2026-04-26  
**Status:** Founder-approved direction for Team implementation  
**Applies to:** `trust.iai.one` Phase 1

## 1. Purpose

This document locks the role boundary of `trust.iai.one` so the team does not accidentally turn it into:
- a replacement for `iai.one`
- a second home portal
- a second app shell
- a second developer portal
- a second VC/proof/NFT product surface
- a super-page that mixes everything together

`trust.iai.one` exists to make the system more trustworthy, not more confusing.

## 2. Core Principle

`trust.iai.one` is an **Operational Trust Surface**.

It is **not**:
- the constitutional root
- the main routing portal
- the application layer
- the developer documentation hub
- the proof issuance product
- the credential verification product
- the NFT/provenance product

Its job is to answer one question clearly:

**How can a human or organization verify what is official, what is proven, what is declared, and what is still unverified?**

## 4. What `trust.iai.one` must do

`trust.iai.one` must do only the following:

1. Publish the official list of approved domains and subdomains
2. Publish the official list of teams and responsibility boundaries
3. Publish the official communication and reporting channels
4. Explain how verification works
5. Show trust status using proof or disclosure
6. Allow trust pages to be created and published
7. Allow public reporting of impersonation, mismatch, or stale claims

## 5. What `trust.iai.one` must not do

`trust.iai.one` must not:

1. Act as the main home page of the ecosystem
2. Become the main application shell
3. Replace `developer.iai.one`
4. Replace `docs.iai.one`
5. Replace `vc.vetuonglai.com`
6. Replace `proof.tranhatam.com`
7. Replace `nft.iai.one`
8. Host private operational dashboards in public mode
9. Expose private repository structures or sensitive internal routing
10. Claim more certainty than the current proof allows

## 6. Public language rule

All public language on `trust.iai.one` must follow this standard:

- If a claim is supported by public proof, label it **Verified**
- If a claim is officially stated but not yet publicly provable, label it **Declared**
- If a claim cannot yet be verified, label it **Unverified**

No sentence should sound stronger than its evidence.

## 7. Phase 1 scope boundary

Phase 1 is **static-first** and **evidence-led**.

Phase 1 includes:
- public trust modules
- public trust labels
- public disclosures
- public trust pages
- report mismatch form
- stale flag

Phase 1 does not include:
- heavy backend workflows
- deep internal audit logs
- private repo evidence exposure
- admin-only operational systems
- secret infrastructure maps
- model-specific AI telemetry

## 8. Ownership boundary

### Founder
- approves scope
- approves trust role boundary
- approves escalation decisions

### Team Admin / Trust PMO
- maintains domain registry
- maintains ownership registry
- reviews stale claims
- reviews mismatch submissions

### Product teams
- provide factual inputs for their own surfaces
- do not redefine trust labels on their own
- do not publish unsupported trust claims

### Trust implementation team
- implements the trust surface
- follows this document strictly
- escalates ambiguity rather than improvising role expansion

## 9. Escalation rule

If any requested feature would make `trust.iai.one` behave like:
- a product app
- a root portal
- a docs portal
- a payment portal
- a developer hub
- a proof issuance system

the team must stop and escalate to founder review before implementation.

## 10. Final instruction to the team

Build `trust.iai.one` as a **truth surface**, not a super-site.

When in doubt:
- reduce scope
- downgrade the claim
- show disclosure
- escalate ownership or role ambiguity
