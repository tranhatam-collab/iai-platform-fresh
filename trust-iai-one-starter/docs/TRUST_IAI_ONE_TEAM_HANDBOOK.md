## 1. The one rule that overrides everything

Every public statement on trust.iai.one must be one of:

- **Verified** — backed by inline evidence on the page
- **Declared** — officially stated, but public proof is incomplete, summarized, or internal-only
- **Unverified** — page openly says what is not verified, why, and when it will be reviewed again

Anything that is not one of these three must be removed. There is no "almost verified" and no "trusted by us".

## 4. Foundation sync rules

The 2026-04-26 foundation pack is now active. Before a team member changes code, content, or data, verify the change against:

- `TRUST_ROLE_BOUNDARY.md` — keeps trust.iai.one from becoming home, app, developer, proof, VC, or NFT surface.
- `TRUST_CLAIM_STANDARD.md` — every claim must be Verified, Declared, or Unverified.

- `TRUST_PUBLIC_VS_INTERNAL_DISCLOSURE_POLICY.md` — public mode must not leak private repo, agent, infra, telemetry, or contact detail.
- `TRUST_PHASE1_ACCEPTANCE_CRITERIA.md` — release cannot be called done until trust logic, disclosure logic, stale logic, and boundary logic pass.

Active Phase 1 module map:

1. Official Domains

4. Verification Methods
5. `/go/*` Short Links
6. Report & Impersonation
7. Trust Page Builder

If current code still renders an older module name, treat that as migration debt and do not add new features on top of the older map.

## 5. Editing rules

### When changing public copy
- Edit `content/vi.json` and `content/en.json` together. Do not let one language drift.
- Do not introduce English-only or Vietnamese-only marketing words.
- Reject any phrase like "the future", "best in class", "trusted by", "ethical AI" unless the page can show evidence beside it.
- Use only the labels Verified, Declared, or Unverified. Do not use "Partially verified" in new public copy.

### When adding a domain
- Append to `APPROVED_DOMAINS` in `scripts/trust-state-builder.mjs`.
- Re-run `npm run trust:build-state` and inspect `docs/verification-log.md`.
- If the domain is not probable yet, leave it in the list — the builder will route it into `outside_phase_1_scope` automatically.
- Each domain item must include role, owner team, legal lane when known, public evidence or disclosure, last reviewed date, and stale threshold.

### When adding any trust item
- Include `id`, `title`, `status`, `summary`, `evidence_url` or `evidence_reference`, `disclosure`, `last_reviewed_at`, `stale_after_days`, `owner_team`, and `public_visibility` where applicable.
- Set `public_visibility` to `public` before the item can appear in public mode.
- Downgrade to Declared when evidence is official but not fully public.
- Downgrade to Unverified when proof is missing or stale.

### When adding a limitation
- Add to `docs/known-limitations.md` with a new ID.
- Mirror to the `limitations` array in the builder.
- Re-build and verify the limitation is still available in generated trust-state data or the verification log. The active public module map no longer uses a standalone Limitations module.

### When publishing an incident
- Follow `docs/incidents/README.md`.
- Add to the `incidents` array in the builder.
- Re-build and verify the incident remains governed by the incident process. The active Module 6 is Report & Impersonation, not a public incident feed.

### When changing AI disclosure
- AI disclosure wording lives in `content/{vi,en}.json` and the builder's `ai_disclosure.public_statement_*` field until the module migration is complete.
- Do not insert specific model names, vendor names, or internal session identifiers in public copy.
- The footer disclosure must continue to read: "This page may be AI-assisted and human-reviewed. Build evidence is available in the verification log."

## 6. The three checkpoints

Phase 1 ships through three founder checkpoints. Each one is the gate to the next.

### Checkpoint 1 — Builder output review
Deliverables:
- `scripts/trust-state-builder.mjs`
- `src/data/trust-state.json` (and the public mirror)
- `docs/verification-log.md`

Founder reviews:
- domain list classification (Verified vs Declared vs Unverified vs outside scope)
- trust label classification (Verified vs Declared vs Unverified)
- AI disclosure level (must be generic)
- stale-flag policy
- foundation contract coverage for all seven active modules

### Checkpoint 2 — Page draft review
Deliverables:
- `public/index.html` with all 7 modules
- `public/site.js` consuming trust-state.json
- `content/{vi,en}.json` complete
- `public/style.css`

Founder reviews:
- wording, proof links, unverified disclosures
- absence of marketing language
- mobile and dark-mode behavior
- no private/internal fields leaking into public mode

### Checkpoint 3 — Pre-deploy smoke
Deliverables:
- successful `npm run dev` smoke session
- smoke checklist passed (Section 7 below)
- README pointing to deployment notes

Founder approves:
- push to repo
- `wrangler deploy`
- DNS CNAME for trust.iai.one

## 7. Smoke checklist (must pass before deploy)

Run through this list in order. Fail-stop on the first miss.

- [ ] No unsupported public claim. Every page section either has inline data or an explicit unverified disclosure.
- [ ] Every trust item renders exactly one status: Verified, Declared, or Unverified.
- [ ] Older "Partially verified" wording is not visible in public copy.
- [ ] Active module map is Official Domains, Official Teams, Official Channels, Verification Methods, `/go/*` Short Links, Report & Impersonation, Trust Page Builder.
- [ ] No slogan-only trust language.
- [ ] No model name or vendor name hard-coded in public copy.
- [ ] No private AI session detail published.
- [ ] No fake incident.
- [ ] No fake SLA.
- [ ] No fake anti-pattern audit results.
- [ ] Domain Registry only shows domains that probed successfully at build time.
- [ ] Domains that failed appear only under "Outside Phase 1 verified scope".
- [ ] Public mode exposes only fields approved by the disclosure policy.
- [ ] Footer carries the AI-assisted-and-human-reviewed disclosure.
- [ ] Module 5 explains `/go/*` short-link scope and does not present unowned links as verified.
- [ ] Module 6 exposes mismatch/stale/impersonation reporting without fake incident or SLA claims.
- [ ] Mobile layout works (≤ 760px width).
- [ ] Dark mode renders correctly.
- [ ] `trust-state.json` exists in both `src/data/` and `public/data/` and they match.
- [ ] `verification-log.md` exists and matches the JSON.

## 8. Deployment

Required Cloudflare resources (founder account):
- D1 database `trust_iai_one_db`
- R2 bucket `trust-iai-one-evidence` (Phase 2 will use it; Phase 1 binding is harmless)
- DNS record: `trust.iai.one` CNAME pointing to the Workers route

One-time setup:
```bash
npx wrangler d1 create trust_iai_one_db
# copy the returned database_id into wrangler.toml
npx wrangler r2 bucket create trust-iai-one-evidence
npm run db:prod
npm run seed:prod   # safe; seed.sql is intentionally empty
```

Deploy:
```bash
npm run deploy
```

## 9. What this surface explicitly does not promise (Phase 1)

- It does not run continuous monitoring.
- It does not provide authenticated user APIs.
- It does not export user data.
- It does not delete user data on demand.
- It does not enforce a disclosure SLA technically.
- It does not certify content correctness of any other domain.

If a user requests any of the above, point them at Module 7 or the email fallback.

## 10. When something on the page becomes wrong

1. Open the relevant source file (builder, content JSON, or limitations doc).
2. Fix it.
3. Re-run `npm run trust:build-state`.
4. Verify locally with `npm run dev`.
5. Commit with a message that names what was wrong and what changed.
6. Deploy if the change should be live immediately. Otherwise let the next deploy carry it.

If the wrong claim was already public, also add or update an incident entry per `docs/incidents/README.md`.

---

## 11. Final reminder for any AI agent editing this surface

- Do not invent counts, badges, or timestamps.
- Do not move data from `unverified` or `declared` to `verified` without real public proof.
- Do not publish a trust item without a status, evidence or disclosure, review date, stale rule, owner, and visibility.
- Do not delete `outside_phase_1_scope` entries to make the page look cleaner.
- Do not introduce backend behavior without updating Module 7 disclosure first.
- Do not edit `verification-log.md` by hand — re-run the builder.
- When in doubt, choose the more conservative disclosure. The page works fine when it admits limits. It fails the moment it overstates anything.
